---
title: 首次开放前检查清单
description: 在把地址发给玩家前，用一次完整演练确认服务器能进、能玩、能恢复
---

第一次能启动服务端时，最容易马上把地址发给朋友。但真正的“可以开服”至少包括：普通玩家能连接、核心玩法可用、管理员权限没有放大、备份能够恢复。下面的清单不需要一次完成得很复杂，却能减少开服当天的大多数手忙脚乱。

## 基础环境

| 项目 | 完成标准 |
| --- | --- |
| 服务端版本 | jar、Minecraft 版本和 Java 版本都有记录。 |
| 启动日志 | `logs/latest.log` 没有持续重复的插件、模组或端口错误。 |
| EULA | 已理解并确认 `eula.txt`；不要把它当作可以绕过的步骤。 |
| 启动脚本 | 能从固定目录启动，jar 文件名与脚本一致。 |

## 玩家体验

用一个没有 OP 的测试账号完成：进入服务器、出生、聊天、睡觉、死亡、重生、常用命令和退出重连。若有插件或模组，再测试它们最核心的一两个功能。这样能尽早发现“管理员自己能用，普通玩家不能用”的权限问题。

## 网络与安全

确认公网连接应使用真正的外部网络，例如手机流量；同一 Wi‑Fi 的结果不能覆盖完整路径。小型好友服建议开启白名单，OP 只保留给实际管理员，并检查公开端口是否只有游戏端口。`online-mode`、RCON 和 `server-ip` 的含义可在[对外联机的安全基线](/docs/network/security-baseline)中继续阅读。[1]

## 数据与恢复

开服前做一次整服备份，然后把它解压到隔离目录启动或至少确认归档可以读取。记录备份位置、日期和恢复步骤。Paper 的更新指南将世界、服务端配置、插件配置和插件 jar 都列为需要保护的内容。[2]

## 玩法与公告

在邀请玩家前说清楚版本、地址、白名单申请方式、主要规则、是否启用资源包、是否允许模组客户端、维护时间和问题反馈渠道。规则不需要像合同一样长，但应让玩家知道“可以做什么、出了问题找谁”。

全部通过后，再进入[日常维护清单](/docs/maintenance/routine)。服务器稳定不是一次设置完成的，而是每次变更都保持可验证、可回滚。
