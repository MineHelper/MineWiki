title: 游戏规则、难度与世界边界
description: 用可回滚的方式调整服务器玩法，不把一次命令变成全服意外
---

`server.properties` 决定的是服务端启动时的基础选项；死亡掉落、火焰蔓延、昼夜循环这类玩法规则，通常通过游戏命令或世界数据控制。修改之前先明确它会影响哪个世界、是否立即生效，以及玩家是否已经围绕原规则建设了玩法。

## 难度与默认游戏模式

| 目标 | 常见入口 | 注意事项 |
| --- | --- | --- |
| 调整全服难度 | `difficulty` 命令或 `server.properties` 的 `difficulty` | 已生成的世界不会因此自动修复怪物、物品或玩家状态。 |
| 新玩家的默认模式 | `default-gamemode` | 只影响后续进入或尚未有独立模式记录的玩家；先在测试账号上验证。 |
| 指定新玩家出生区域 | `setworldspawn` | 不是对所有现有玩家强制传送。 |
| 限制可探索范围 | `worldborder` | 应先公告并预留安全区域，避免把玩家建筑或传送点直接隔在边界外。 |

不同 Minecraft 版本可用命令和参数会变化。Paper 提供的权限参考列出了当前服务端可用的原版命令权限；在生产服执行前，可先在控制台输入命令查看该版本的提示与语法。[1]

## 常用 gamerule 的使用方式

`/gamerule <规则> <值>` 会修改当前所在世界的规则。例如：

```text
/gamerule keepInventory true
/gamerule doDaylightCycle false
/gamerule mobGriefing false
```

这些规则不会自动代表所有维度。主世界、下界、末地和多世界插件创建的世界可能需要分别确认。执行前先记下旧值；不确定时用 `/gamerule <规则>` 查询当前设置，再决定是否更改。

| 规则 | 改变什么 | 适合先讨论的问题 |
| --- | --- | --- |
| `keepInventory` | 玩家死亡后是否保留背包与经验 | 服务器想保留怎样的死亡成本？ |
| `doDaylightCycle` | 时间是否自动流逝 | 是否会影响农场、村民和玩家作息？ |
| `mobGriefing` | 部分生物是否能改变方块 | 是否会连带改变村民、农场或生物行为？ |
| `doFireTick` | 火是否扩散与熄灭 | 是否准备以牺牲原版火焰行为换取更低的事故风险？ |

不要把 gamerule 当作“优化参数”。它们主要改变玩法与世界行为；性能问题应先用 spark 和日志定位。[2]

## 世界边界应先规划再执行

世界边界适合控制可探索面积、降低无限扩张带来的管理成本，或为活动制作封闭区域。设置前先决定中心点、半径、过渡时间和边界外玩家如何处理。

建议流程是：先在测试服用小数值体验一次，再在正式服公告变化，设置缓慢过渡时间，最后确认传送点、出生点和常用建筑都位于安全区域内。需要预生成区块时，应单独评估磁盘和 CPU 负载，不要与边界变更、插件更新混在同一次维护中。

## 修改后的验证清单

1. 用非 OP 测试账号确认规则对普通玩家的实际体验。
2. 分别进入主世界、下界和末地，确认目标世界是否都符合预期。
3. 观察 `logs/latest.log` 是否有命令或插件报错。
4. 将规则、原因和日期记入维护记录；这能避免几个月后没人知道“为什么这个服永远是白天”。
