title: 客户端与服务端模组兼容

---

模组服玩家进不来时，最常见的答案是“版本没对齐”，但这句话还不够具体。模组可能只在客户端运行、只在服务端运行，或要求两端安装。正确做法是核对每个模组作者声明的运行环境、Minecraft 版本、加载器版本和依赖，而不是机械地复制整个 `mods/` 目录。

## 三类模组

| 类型 | 典型作用 | 连接时的要求 |
| --- | --- | --- |
| 客户端专用 | 画面优化、界面、快捷键、光影相关 | 不应被直接放入普通服务端；玩家可按作者说明自行安装。 |
| 服务端专用 | 管理、性能分析、部分玩法逻辑 | 玩家通常不需要安装，但仍要确认作者标注。 |
| 两端都需要 | 新方块、实体、网络协议或共同玩法内容 | 客户端与服务端必须使用兼容的构建和依赖。 |

不要靠模组名字猜类型。发布页、`fabric.mod.json`、`mods.toml`、NeoForge/Forge 元数据或整合包说明才是判断依据。Fabric 官方同样强调，模组必须匹配对应的 Minecraft 与加载器版本。[1]

## 发生不兼容时怎么读信息

玩家客户端和服务端会给出不同侧的错误。优先保留以下内容：

1. 客户端连接界面的完整错误消息或日志片段。
2. 服务端 `logs/latest.log` 中同一时间的连接记录。
3. Minecraft、加载器、模组、依赖库的完整版本号。
4. 最近新增、更新或删除的模组列表。

看到 `missing dependency`、`requires`、`incompatible` 或某个具体 mod id 时，先处理它点名的第一个问题。后续异常有时只是前置依赖失败的连锁结果。

## 建议维护一份版本清单

小型整合包也值得保存一份清单，至少记录：Minecraft 版本、加载器版本、Java 版本、服务端模组列表、客户端额外模组、配置包版本和发布日期。每次更新前复制旧清单，更新后再生成新清单。

这样当某个玩家反馈“昨天能进，今天不能进”时，你可以直接比对变更，而不是让所有人重新下载一遍。

## 服务端为什么不应随意放客户端模组

纯客户端模组可能引用图形、界面或客户端专用类。放进服务端后，通常会在启动时抛出环境不匹配错误；更糟的是，有些模组在特定版本下才暴露问题。使用整合包作者提供的 server pack 可以减少这类错误，但仍应阅读安装说明并验证启动日志。[2]
